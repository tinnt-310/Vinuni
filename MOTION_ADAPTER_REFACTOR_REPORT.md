# `motion_adapter.cpp` responsibility inventory — 2026-09-27

Status: **audit in progress; not an accepted architecture**. The 2,500+ line `MotionAdapter` still combines ROS, MoveIt, motion policy, safety and telemetry. The single initial Git commit already contains this split package, so historical `fr10_pose` copy/paste counts are not demonstrable. This file is an input to the mandatory whole-workspace [granularity audit](MODULE_GRANULARITY_AUDIT.md), not a substitute for it.

`R` means ROS/MoveIt-dependent; `D` means a decision better owned by ROS-free domain code; `W` means worker-side blocking work; `T` means 125 Hz tick or monitoring callback; `I` means infrastructure/lifecycle. “Runtime” coverage means a launched ROS/Gazebo/SimMachine path, not an isolated unit test.

## Current ownership and coupling risks

`MotionExecutor` owns active execution state and is written only by the control runner. `InsertionSequenceState` now owns pending/retained insertion targets and duplicate checks behind one mutex; `MotionAdapter` still owns task sequence, accepted/queued targets, reversal task and stop latches. These are related but not one explicit task FSM. The worker and callbacks still coordinate target/replan state through several owners. The next extraction must introduce a policy coordinator with explicit transition inputs/outputs and tests for stop, stale plan and retract. No second ServoJ/FAIRINO execute path may be introduced.

## 2026-09-27 bounded ownership extraction

`insertion_sequence_state.hpp` centralizes pending staging generation, retained socket target, duplicate-target comparison, stop/rejection rollback and retract snapshot. The adapter no longer holds three separate insertion mutex/state fields. Pure tests cover matching versus unrelated generations, direct insertion, duplicate suppression, retract retention and stop clear. This is state ownership only: pose geometry, policy transitions, PlanningScene work, ROS lifecycle and diagnostics are still mixed in the adapter. No public ROS interface, servo limits or backend path was changed.

Full acceptance remains blocked on a tested policy coordinator, scene-aware planning service, diagnostic separation and whole-workspace per-file audit. The actual `fr10_pose_controller_node` was exercised with ros2_control GenericSystem: joint and one-shot insertion passed, but the legacy 10 Hz pose-stream smoke case failed under safety rejections. See [FR10_AUDIT_REGRESSION_REPORT.md](FR10_AUDIT_REGRESSION_REPORT.md) §11; no physical FAIRINO hardware was used.

## 2026-09-27 strict-axis boundary and runtime findings

`LinearInsertPlanner::validateAxis` now owns the insertion/retraction axis decision in the ROS-free domain, including the existing straight-segment plan, perpendicular tolerance and signed forward projection. The adapter supplies measured FK and logs the structured result. The test went red before the API existed and green with forward, retraction, lateral, reverse and nonfinite cases; no configured limit or public topic changed. Five-package build passed; FR10 CTest 67 total with 0 failures and one intentional skip, vehicle_bringup 2/2. See [main report](FR10_AUDIT_REGRESSION_REPORT.md) §12 for the 27 valid V0–V8 measurements and separate simulator crash.

This extraction exposes an inherited scheduling violation: `controlTick` calls `queueInsertionAfterStagingIfReady`, which can call `queueStrictInsertionTarget` and now `validateAxis`; the latter invokes `LinearInsertPlanner::plan` and builds a dense path on the 125 Hz tick. Moving that work to the planning worker while preserving the measured PRE_INSERT boundary and single executor writer is still required. The node remains 2,495 lines and is not a genuine adapter-only component.

On post-change ros2_control GenericSystem, one-shot INSERTION passed in one run at 1.53e-6 m error, but another run and the 10 Hz stream each encountered `Robot feedback read failed` / `COMM_FAILURE`. The configured freshness gate is 50 ms; the exact failing condition has not yet been isolated. The earlier no-dropout run independently failed the final streamed goal after stale-plan/timing rejections. Neither failure is hidden by the pure axis test; safety checks remain unchanged. A worker cancellation also overwrote the stop-reason label after `COMM_FAILURE` in the repeated log, a diagnostic/state-ownership race to address alongside the coordinator decomposition.
## 2026-09-27 bounded retarget recovery and lightweight boundary check

The earlier 10 Hz stream failure above is superseded by three independent post-recovery GenericSystem passes. The actual node now handles a moving-boundary scalar timing failure by retaining the goal, making one jerk-limited controlled stop, and replanning at HOLDING. A separate per-goal counter bounds this timing stop independently of stale-activation reseeds. A stationary timing failure still rejects. Stale activation allows three live reseeds, then one controlled-stop pose replan, then rejects. The trajectory timing test exercises moving and stationary failure outcomes; the policy test exercises both retry bounds. No velocity, acceleration, jerk, reference-lead or feedback-freshness limit was relaxed.

The 125 Hz insertion boundary no longer builds a dense waypoint vector. `LinearInsertPlanner::checkAxis` makes the bounded O(1) axis decision, sharing `CartesianPath::linearSegmentCount` with the full worker-side path. Pure tests cover forward, reverse, lateral, nonfinite and capacity cases. The adapter still performs bounded measured analytical FK and bookkeeping on that tick; this change does not make the node adapter-only. The preceding scheduling warning about dense path construction is therefore resolved, while larger planning/policy ownership remains unresolved.

After these edits, five selected packages built, FR10 CTest reported 68 total with 0 failed and 1 intentional skip, vehicle_bringup CTest passed 2/2, and readiness tests passed 4/4. Three stream runs and one post-axis run each passed startup, joint, one-shot insertion and 20 changing poses at 10 Hz; the final target reached HOLDING/GOAL_REACHED with about 1.53e-6 m TCP error and no SDK/write errors. See [main report](FR10_AUDIT_REGRESSION_REPORT.md) §13 and its raw-result links. These runs do not establish immunity to the intermittent 50 ms feedback dropout. Full scene-planning, policy and diagnostic separation; stop-reason ownership; whole-workspace audit; Docker and physical-hardware validation remain open.

## 2026-09-28 stop-reason ownership correction

Planning worker rejection sites could overwrite `COMM_FAILURE` after a fail-closed stop. A ROS-free `stop_reason_policy.hpp` now arbitrates worker reports with an atomic compare-and-swap: worker outcomes may replace `NONE`, a previous `GOAL_REACHED` or an older `IK_FAILURE`, while latched stop/fault reasons remain intact. Seven worker stores now use this rule. The 125 Hz control runner remains the sole `MotionExecutor` writer. Pure `stop_reason_policy` tests cover communication and reference-lag fault precedence, shutdown and a subsequent goal. A and C current-build smoke passed and 69 FR10 CTests reported no unexpected failure. Full pose policy/planning service/diagnostics decomposition is still outstanding.
